1. Finish state

Treat the work as one product flow. A visible control is not completion. The source, document, sidecar, preview, filmstrip, cache, undo history, batch path, and export must agree.

Run rule

Each execution step ends with a Gate. Advance only when every condition in that Gate is true. When a step points to issue contracts, read those contracts before editing code.

Library context

Develop retains the Library album, folder, archive state, filters, sort order, active photo, and selection after navigation and hard refresh.

Versioned edits

v2 remains frozen. v3 has strict codecs, one owner for each value, an explicit upgrade, a rollback payload, and visible compatibility errors.

One render plan

Preview and export compile the same semantic stages. Quality, dimensions, overlays, and output intent are explicit request differences.

Honest capabilities

The UI identifies 8-bit input, embedded RAW preview, missing profiles, missing assets, stale jobs, SDR display, and unsupported output.

Complete tool behavior

Every sampler, automatic action, guided action, and generated job has Cancel, error or no-result state, one acceptance point, and one undo group.

Connected PR

The implementation ends in one PR. The PR targets the default branch and connects every completed issue with a closing keyword.

Boundaries

  • Keep Adobe private process data outside Darkroom's schema.
  • Keep HDR merge outside issue #61.
  • Keep AI Denoise #73 outside standard noise reduction.
  • Keep AI Sharpening #74 and export output sharpening outside Develop sharpening.
  • Support only decoder, profile, display, and encoder capabilities that the app can report and verify.
  • Limit the Library change to Develop context preservation and batch entry points.

2. Run rules

These rules apply to every step. The repository remains the source of truth for commands, code shape, and current instructions.

  1. Read the repository AGENTS.md before code changes. Preserve unrelated user files and dirty-tree changes.
  2. Before changing a Next.js route or convention, read the matching guide in node_modules/next/dist/docs/.
  3. Keep React and Zustand as adapters. Put persistence, render order, batch loops, stale-job checks, and export behavior behind the Develop session.
  4. Keep the frozen v2 decoder and renderer available throughout the work. Create v3 beside it.
  5. Use typed diagnostics for every fallback. A fallback is part of the user-visible result.
  6. Use existing checks and record the manual workflow. Get explicit approval before adding test files, as required by this repository.
  7. Keep each change inside the current step. Move duplicated orchestration only after its callers use the new owner.
  8. Record every Gate result for the PR body. A failed Gate remains open work.

Escalate these decisions before feature work

  • The v3 working color space does not pass camera-profile, saturated-color, gradient, HDR, and proof fixtures.
  • The target Electron platforms cannot provide typed high-bit decode, intermediate render targets, or full-resolution output.
  • No acceptable licensed camera profile, lens profile, local removal model, or depth model is available.
  • The v2 baseline cannot be reproduced after the session or compiler boundary is added.

5. Render reference

Load this section in Steps 0, 3, 4, 5, 6, and 9. The v2 plan stays frozen. The v3 compiler emits this fixed semantic order for preview and export.

v2 process

Keep the current decoder choices, defaults, shader order, math, preview policy, and 8-bit export path. Existing documents stay here until an accepted v3 upgrade.

v3 process

Use typed source pixels, a versioned working space, high-bit intermediates, named analysis taps, a canonical coordinate model, and typed output.

v3 semantic order

  1. Decode and orientationDecode or demosaic typed pixels. Record precision, transfer, dimensions, EXIF orientation, and embedded-preview provenance.
  2. WB and input profileApply selected WB in source space. Apply the input profile and camera calibration into the working space.
  3. OpticsApply lens distortion and illumination. Apply chromatic aberration and defringe.
  4. Standard denoiseApply luminance and color noise reduction once at source-pixel scale.
  5. Canonical geometryCompose user turns, flips, angle, Upright, perspective, Constrain Crop, and crop through one coordinate model.
  6. Source repairComposite accepted Heal, Clone, Remove, red-eye, and distraction patches in their declared source-repair frame.
  7. Basic toneApply exposure, contrast, highlights, shadows, whites, blacks, vibrance, saturation, and accepted Auto Tone values.
  8. Curve and colorApply curve, Point Color, HSL mixer, the B&W branch, and Color Grading.
  9. Local adjustmentsResolve masks through the coordinate model and apply local values at named stage taps.
  10. PresenceApply Texture, Clarity, and Dehaze with edge-safe source-relative kernels.
  11. Creative spatial effectApply Lens Blur from a current source-signed depth asset.
  12. Develop sharpeningApply amount, radius, detail, and masking once.
  13. Post-crop effectsApply vignette and grain.
  14. Resize and tile assemblyResolve fit, loupe, or export dimensions. Render full output through overlapping tiles.
  15. Output or proof transformConvert working pixels to the requested display, proof, or output profile and SDR or HDR transfer.
  16. Analysis, overlays, and encodeRead histogram, clipping, HDR headroom, and gamut taps before transient overlays. Encode typed pixels and metadata.

Named analysis taps

  • tone-input is the full-frame output of Source repair, stage 6. It excludes current tone, curve/color, local adjustments, presence, blur, sharpening, and post-crop effects.
  • wb-sample is source-linear data with the canonical coordinate map.
  • display-output is output-transformed full-frame data before overlays.
  • scene-headroom is scene-linear data before SDR mapping.
  • proof-output is proof-transformed data plus the out-of-gamut mask.
