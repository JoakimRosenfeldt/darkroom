Library flow rework agent runbook

Rework organize, search, cull, inspect, and duplicate review around one scoped and ordered library result. Deliver the work as small pull requests. Every pull request must name its GitHub issues, and only the pull request that satisfies an issue's full closure gate may close it.

Operating rule: start with the next ready package in the delivery map. Read its linked issue before editing. Finish with a verified pull request that uses Refs, Part of, or Closes exactly as defined below.

01 / Execution

Execution protocol

This loop applies to every package. The issue body supplies branch-specific product context. This runbook supplies order, shared contracts, and integration rules. Repository instructions in AGENTS.md remain in force.

1
Select one ready package. Confirm every dependency named in the delivery map is merged. Read AGENTS.md, the package card, its shared contracts, and every linked issue body.
Complete when the branch has one stated package goal and no unmet dependency.
2
Write the task boundary before editing. Record Goal, Scope, Context, Constraints, and Verification in the working note or agent prompt. Name the files likely to change and what is out of scope.
Complete when another agent could implement the package without choosing a different product direction.
3
Establish the current behavior. Reproduce the package's primary case in Electron and record the visible result. For migrations, copy a catalog before loading it. Do not add a new test suite unless the user asks for tests.
Complete when the before state and expected after state are both observable.
4
Implement the smallest coherent slice. Follow existing module boundaries. Keep filesystem authority in Electron. Keep derived library results out of persisted catalog data. Add a dependency only after the package's dependency gate passes.
Complete when the package goal works without placeholders, parallel implementations, or unrelated refactors.
5
Connect the shared result. Route grid, counts, selection, filmstrip, viewer navigation, culling, and compare through the shared library result when the package affects scope or order.
Complete when two UI surfaces cannot derive different entry sets for the same state.
6
Verify the package. Run the required commands, execute the package's manual cases, restart Electron, and check the linked issue's completion criteria. Record known repository-wide lint failures separately from new diagnostics.
Complete when the pull request can state what passed, what failed, and why.
7
Review the blast radius. Check catalog migration, persistence, path safety, visible order, selection restoration, and source-file behavior as applicable. Inspect the final diff for unrelated changes.
Complete when each material risk has either a passing check or an explicit pull request note.
8
Open the connected pull request. Use the repository's file-pr skill. Follow the issue-link rules in the next section. Do not mark a partial implementation as closing an issue.
Complete when the pull request is open, checks are reported, and every affected issue is linked with the correct keyword.

Task brief template

Goal
What must be true when this package is done.

Scope
Files and modules to change. State what is out of scope.

Context
Linked issue bodies, relevant package dependencies, current behavior, and shared contracts.

Constraints
Catalog compatibility, filesystem boundaries, API contracts, ordering rules, and repository instructions.

Verification
Commands and observable Electron cases that prove completion.
02 / Delivery record

Pull request rules

Default shape

  • Use one branch and one pull request per package.
  • Keep foundational model work separate from its UI closure slice.
  • Merge packages in dependency order.
  • Use the file-pr skill when opening each pull request.
  • Do not combine packages because they touch the same file.

Issue keywords

  • Refs #34: relevant foundation or supporting work.
  • Part of #34: a required slice that does not satisfy the full issue.
  • Closes #34: the issue body and every completion criterion pass after merge.
  • Put each closing keyword on its own line when one pull request completes several issues.

Closure guard: a closure package inherits the earlier supporting packages for that issue. Before writing Closes, rerun the whole issue checklist against the merged dependency state. A green package check alone is not enough.

Required pull request body

## Problem
State the user-visible gap and current behavior.

## Solution
State the implemented package boundary and shared contracts used.

## Issues
Refs #137
Part of #34
Closes #140

## Verification
- npm run build
- Changed-file lint or repo lint result
- Electron cases, including restart

## Risk and rollback
Catalog migration, filesystem, ordering, or performance risks when applicable.

If the whole program is deliberately delivered on one branch, the final pull request may list all 15 Closes lines only after all program exit checks pass. Smaller pull requests remain the default.

03 / Product boundary

Outcome and boundaries

Program outcome

A user can browse a folder subtree, organize photos into manual and saved collections, find photos by text and metadata, group related frames, inspect and compare them, cull in visible order, archive without losing organization, and review byte-identical files safely.

Every surface consumes one derived result: active scope, search, facets, curation filters, format, deterministic sort, and stack projection.

Completion standard

  • All 15 issue closure gates pass in Electron after restart.
  • Catalog migrations preserve current metadata and albums.
  • Grid, counts, viewer, filmstrip, compare, and culling agree on scope and order.
  • Every package has a connected pull request and recorded verification.
  • No action deletes a source file outside an explicit, confirmed OS-trash flow.

Decisions fixed for this program

AreaDecisionReason
CatalogKeep one local JSON catalog per root. Add explicit parser migrations and atomic replacement.The current product is local-first and needs no database for these issues.
Entry identityKeep encoded relative-path entry IDs for this program.A stable-ID migration changes import, rename, sidecar, and deletion semantics beyond the requested work.
CollectionsUse one tree containing sets, manual albums, and Smart Albums. The root is virtual.One hierarchy avoids separate navigation and ordering systems.
Tree movementUse explicit menu actions for move and sibling reorder. Do not require drag and drop.The issue permits menu-based movement and keyboard use is easier to verify.
SearchUse normalized, case-insensitive, diacritic-insensitive substring matching. Whitespace tokens use AND.The rule is deterministic and useful for names, paths, and indexed metadata.
FacetsUse OR within one facet and AND between facet types. Counts exclude the facet being counted.Users can predict the result and still see available alternatives.
LocationUse embedded city, state, country, and a GPS-present value. Do not reverse geocode.Reverse geocoding adds network, privacy, cache, and locale work.
Capture dateUse embedded capture time. Put missing or invalid dates in a missing bucket with path tie-breaking, never disguised as modification time.The sort label must mean capture date.
DuplicatesDetect exact byte matches only. Use OS trash for source removal.Visual similarity and permanent deletion are separate safety problems.
RefreshProvide explicit refresh. Do not add a filesystem watcher.External rename and deletion need reconciliation, but continuous watching is not required.
TestingUse existing checks and an explicit Electron matrix. Do not add tests unless requested.This follows repository instructions while keeping completion observable.

Out of scope

Multiple library roots, a database, stable file identities across external rename, cloud sync, reverse geocoding, visual-similarity detection, face recognition, a filesystem watcher, permanent file deletion, and a general drag-and-drop tree framework are not part of this program.

Phase 0

Build the shared base

0A. Make catalog writes durable and migrations explicit

Refs #29 #30 #31 #32 #34 #36 #39 #140 #143

Goal: later packages can add persisted state without risking a partial JSON file or scattering migration logic.

Scope
lib/catalog/types.ts, lib/catalog/persistence.ts, electron/catalog-store.ts, preload/main catalog contracts.
Constraints
Keep one JSON file per root in Electron user data. Read catalog versions 1 and 2. Do not predict or pre-add fields for later features.
Complete when
A copied v1 and v2 catalog load to the current in-memory shape; a forced interrupted write leaves either the prior valid file or the full new file; parse and write errors reach visible UI state.
Steps
  1. Centralize the latest writable catalog version and one migration path per version.
  2. Validate before writing. Write a sibling temporary file, flush it, then atomically replace the target. Keep one last-known-good backup before a schema migration.
  3. Expose write failure through the persistence queue instead of swallowing it. Keep later writes serialized per root.
  4. Document the rule: the package that adds persisted fields owns its version bump, parser, migration, pruning, and restart check.

0B. Introduce one library result resolver

Refs #137 #30 #31 #32 #33 #34 #40 #140 #142

Goal: one pure contract controls active scope, filters, deterministic order, projected stack tiles, and selection reconciliation.

Scope
New focused module under lib/library/, app/page.tsx, app/photo/page.tsx, stores/library-store.ts.
Constraints
Do not persist derived result arrays. Keep current behavior for unsupported future view kinds.
Complete when
Grid and viewer receive the same ordered IDs for All, Folder, Album, and Archive; changing scope reconciles selection to a visible ID or clears it; no page performs its own sort chain.
Steps
  1. Define resolveLibraryResult(input) and the output contract in Shared contracts.
  2. Move the current archive, catalog-view, curation, format, and sort chain into the resolver without changing visible behavior.
  3. Make app/page.tsx render the result and app/photo/page.tsx navigate its ordered IDs.
  4. Centralize selection reconciliation against the result and preserve an existing selected ID when it remains visible.

0C. Hydrate normalized file metadata in the background

Refs #33 #34 #39 #140

Goal: capture time, search fields, facet fields, and file fingerprint inputs are available without decoding files during render.

Scope
Filesystem scan types and service, Electron IPC/preload, catalog entry analysis fields, new query-index module under lib/library/.
Constraints
Parsing runs in Electron with bounded concurrency. The renderer receives typed values, not raw absolute-path authority. Search indexes stay in memory and are rebuilt from persisted source fields.
Complete when
Import returns thumbnails and entries before analysis ends; progress and cancellation work; unchanged files reuse fields by size and modification-time cache key; one changed file invalidates only its index record.
Steps
  1. Define typed source fields for capture time and provenance, camera make/model, lens, ISO, focal length, embedded location, GPS presence, size, and modification time.
  2. Run a decoder gate against supported JPEG, HEIC, TIFF, and available RAW fixtures. Add exifr only if it parses the required fields for supported formats and packages cleanly; otherwise use the current decoding path and report unsupported values as missing.
  3. Add cancellable, bounded metadata work after the scan's first usable result. Persist normalized source fields with a cache signature.
  4. Build per-entry normalized search text and facet indexes in memory. Never parse display strings to evaluate a query.

1D. Sort by embedded capture time

05 / Single source of truth

Shared contracts

These rules prevent later packages from creating a second implementation. Keep each definition beside the module that enforces it.

Catalog and persistence

  • parsePhotoCatalog accepts supported stored versions and returns only the latest in-memory shape.
  • The feature package that adds persisted fields also adds its version, migration, validation, pruning, and restart case.
  • Unknown future versions fail with a useful message. Malformed current data names the failing path.
  • Writes validate first, use a temporary sibling, replace atomically, and remain serialized per root.
  • A migration keeps one last-known-good backup. Derived search results, facet counts, and Smart Album memberships are never stored.

Shared library result

resolveLibraryResult({
  entries,
  catalogState,
  primaryScope,
  textQuery,
  facets,
  curationFilter,
  formatFilter,
  sort,
  expandedStackIds
}) => {
  matchingEntryIds,
  visibleItems,
  viewerEntryIds,
  photoCount,
  tileCount,
  facetCounts,
  revision
}
  1. Resolve valid entries and the primary scope: All, Folder, Manual Album, Smart Album, Quick, Archive, or Duplicates.
  2. Apply archive visibility required by that scope.
  3. Apply text query.
  4. Apply facets using OR within and AND between.
  5. Apply curation and format filters.
  6. Sort entries with deterministic tie-breaking.
  7. Project stacks into visible items. Keep the ordered matching IDs available for counts and explicit stack entry.

Consumer rule: grid, folder counts, toolbar counts, selection ranges, viewer, filmstrip, auto-advance, and compare receive this result or a named projection of it. They do not rebuild the pipeline.

Metadata and query

  • Persist typed source values and provenance. Build normalized search text and bucket indexes in memory.
  • Index invalidation keys are entry ID plus file size and modification time for file metadata, and explicit revisions for catalog metadata, albums, keywords, archive, and Develop.
  • Search tokens use AND. A token may match any indexed field by substring after case and diacritic normalization.
  • Facet counts apply every active constraint except the facet being counted.
  • Capture date never falls back silently to modification time. Missing stays a named state.
  • Metadata hydration and hashing are cancellable Electron jobs with monotonic job IDs so stale results cannot overwrite newer work.

Collections, keywords, and stacks

  • One collection tree owns sets, manual albums, and Smart Albums. Only manual albums store entry membership.
  • Quick Collection stores ordered unique IDs. Target stores a valid manual album ID or null.
  • Smart rules are validated data with bounded depth and node count. They never contain code or cached member IDs.
  • Keyword assignment stores direct IDs. Ancestor and descendant behavior is derived from the cycle-safe tree.
  • An entry belongs to at most one stack. Archive hides but retains membership. Source removal prunes. A stack with fewer than two valid members dissolves.
  • Delete actions remove organization records only unless an explicit source-trash confirmation says otherwise.

Viewer, culling, and compare

  • Viewer order comes from the shared result and is captured with a result revision.
  • The transform owns mode, scale, offset, viewport, crop/rotation bounds, anchor, and clamping.
  • Auto-advance snapshots visible order before the mutation and reconciles against the next result once.
  • Batch curation never auto-advances. Develop edits and navigation never auto-advance.
  • Compare panes share the transform implementation but own independent load/error state. Linked movement maps normalized image coordinates.

Filesystem safety

  • The renderer identifies catalog entries. Electron resolves absolute paths from the active registered root.
  • Electron canonicalizes root and target, rejects escape and symlink escape, and checks the target is a supported file before destructive work.
  • Source removal uses shell.trashItem and a confirmation that lists file count and paths. No permanent delete is added.
  • Catalog mutation follows the result of each OS action and records partial success. A failed file action cannot be reported as a completed batch.
