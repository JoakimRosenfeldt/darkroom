01Goal and finish line

Goal

Replace Darkroom's folder-as-catalog flow with one SQLite database per catalog, several roots per catalog, stable asset IDs, an Electron-owned filesystem boundary, durable operations, and one capability registry for import, view, Develop, and export.

Finish line

The program is complete only when all of these statements are true:

  • Every tracked issue in the issue map has a merged PR whose body closes that issue.
  • Every asset uses a stable ID that survives rename, move, relink, root change, and catalog path change.
  • The renderer sends catalog IDs, asset IDs, root IDs, or picker grants. Electron resolves authoritative paths.
  • Every mutating item recovers from its last safe stage after process or app restart. The test harness can inject a fault at each safe stage.
  • Cancellation stops native work at a documented boundary and stale events cannot replace a newer catalog session.
  • Migration preserves every recoverable v1/v2 relation and leaves the legacy source untouched until v3 passes validation.
  • The packaged format and camera report agrees with the code path used by scan, preview, Develop, and export.
  • Copy as DNG is either proved by #89 or shown as unavailable. Simulated Nikon output never ships as native support.
  • Catalog backup, validation, optimize, import/export, and restore cannot silently replace or damage the active catalog. Restore preserves filesystem facts that occurred after the selected backup.

02Rules every step must preserve

Identity

Stable

CatalogId, RootId, AssetId, OperationId, and PresetId are random stable IDs. A path is a location, never identity.

Authority

Electron-owned

Electron owns canonical paths, grants, containment, no-follow checks, native work, and catalog files. Renderer code owns display and user intent.

Recovery

Journaled

A frozen plan is immutable. Each file advances through named safe stages and an idempotent database item.

Truth

Observed

Watcher events are hints. Reconciliation proves filesystem state. Package probes and fixtures prove format/camera capability.

Working rules

  • Read the repository instructions and the relevant Next.js 16 guide before editing code in that branch.
  • Inspect the current issue body before starting its step. Treat the issue body and this runbook as one contract. Record any conflict in the PR.
  • Use current project files as the source for scripts, dependencies, and layout. The baseline links in this document explain the old seam; they do not override current code.
  • Make the smallest coherent change for the current step. Keep future-step UI and abstractions out.
  • Preserve unrelated work. Stop if a concurrent edit overlaps the same file and intent cannot be reconciled safely.
  • Add only verification code required by an issue body or needed to prove a new invariant. Use the existing checks and Electron scenarios for the rest.
  • Finish the current step and its PR before starting a dependent step. Parallel work is limited to branches named as parallel in the sequence.

Stop conditions

  • Stop before DNG implementation when #89 has no qualified backend or packaging decision. Keep #20 open and expose the unavailable state.
  • Stop before claiming Nikon native support when runtime licensing, package contents, or architecture support is unresolved. Ship an accurate unavailable state.
  • Stop before enabling Auto Import Move on network ingress until the disconnect and source-cleanup proof passes. Copy remains the default.
  • Stop before destructive catalog replace or restore when the safety backup or staged validation cannot complete.
  • Keep the current catalog active when a nonterminal file item cannot reconcile or the external restore envelope cannot be written and synced.

03PR protocol

Required handoff

Every implementation step ends with a pull request. Invoke the repository's file-pr workflow after the proof passes. Connect the PR to every issue named by that step.

Issue connection rule

  • Use Refs #N when the PR advances an issue but does not satisfy its full close gate.
  • Use Closes #N only when that PR and its dependencies satisfy every completion criterion in the current issue body and the issue map.
  • When several PRs advance one issue, every earlier PR uses Refs. The last proven PR uses Closes.
  • Connect dependency issues too. Example: the DNG PR uses Closes #20 and Refs #89 only after #89 has already supplied the qualified backend.
  • Leave the issue open when one platform, restart path, cancellation path, or packaged capability remains unproved.

PR body

## Problem
Name the user-visible gap this step fixes.

## Change
List the behavior and the hard invariant added by this PR.

## Proof

PR proof

A PR is ready when its step proof passes, the diff stays inside scope, all named issue connections appear in the body, and the branch has no unexplained new check failure. Attach the operation summary, migration report, support matrix, or screenshots when that artifact is the proof.

Prove duplicates before import writes

Close candidate #21

Goal

Detect catalog and session duplicates across rename, then require an explicit resolution.

Scope

Physical boundary

  • catalog-registry.json uses atomic write and stores catalog ID, display name, canonical database path, health, and last-opened time.
  • Each catalog has one SQLite file with WAL, foreign keys, one worker connection, and short transactions.
  • Registry/settings use temporary file, file sync, rename, and parent-directory sync where supported.
  • Cache key is catalogId:assetId:revision:variant.
  • The worker owns backup, integrity, foreign-key check, and compact operations. Main stays responsive.
  • An in-place restore writes one atomic envelope at userData/restore-recovery/<CatalogId>.json, outside the replaceable database. It contains checksums, restore stage, and forward filesystem facts. It is removed after the restored catalog links or records every fact.

R2File operation safety reference

Read this branch when: implementing step 9-11, changing Copy/Move/Rename/DNG/XMP behavior, or reviewing cancellation and crash recovery.

Plan lifecycle

  1. Prepare. Observe sources and classify work. Mutate nothing.
  2. Review. Resolve destination, preset, duplicates, and name conflicts. Mutate nothing.
  3. Freeze. Validate current observations and backend availability. Store immutable plan and hash.
  4. Execute. Advance each item through safe stages. Retain completed items on batch cancel.

Safe stages

plannedIntent and expected source observation stored.
destination-preparedPrivate staged output exists.
destination-publishedVerified final destination exists.
catalog-appliedAsset/location transaction committed.
source-cleanedMove source removed or warning stored.

Commit protocol

  1. Resolve source/destination from current catalog IDs or an unexpired grant. Canonicalize and reject traversal, symlink escape, unsafe overlap, and non-regular source.
  2. Open without following a swapped symlink. Record size, time, and local file identity where available.
  3. Write a private same-directory destination with exclusive create. Stream, hash when required, flush, and verify.
  4. Publish with atomic rename. Explicit Replace uses backup/restore placement.
  5. Apply the catalog transaction after publish and verification.
  6. For Move, remove source after catalog apply. Cleanup failure leaves the destination active and reports source retained.

Same-volume Move/Rename may use native rename. Cross-volume Move uses Copy, verify, publish, catalog apply, then cleanup. Rename/Move retain AssetId. Copy creates a new AssetId.

XMP

  • Discover the image and known XMP as one bundle before mutation.
  • Move/copy known XMP with the image. A changed, missing, malformed, or unmatched sidecar becomes a per-item review state.
  • The catalog is authoritative. Failed sidecar mirroring becomes pending-sync with retry.

R3Scan, watch, and relink reference

Read this branch when: implementing steps 5 or 8, changing filesystem observation, root health, missing state, watcher recovery, or relink matching.

Scan

  • Electron owns the breadth-first walk and emits progress after each directory read and stat batch.
  • Abort before the next directory and between stat batches. An OS call already in flight may finish, but its late result cannot publish.
  • Stage observations. A cancelled, timed-out, failed, superseded, or old-session scan cannot mark assets missing.
  • Commit the completed diff in short transactions and preserve all metadata/relations.

Watch

  • Start root watchers only for the active catalog.
  • Use events to mark paths/subtrees dirty. Debounce burst work and reconcile.
  • Ignore hidden/unsupported paths according to the shared format registry.
  • Persist Watching, Reconciling, Degraded, Missing, and Permission denied states.
  • On overflow/error/network ambiguity, use bounded backoff and a visible Retry scan.
Missing keeps identity. Remove a missing asset from the normal present-files view, but keep its row, metadata, albums, archive, Develop, fingerprint, and last observation until explicit catalog deletion.

Relink match order

  1. Exact SHA-256 is portable proof and may be preselected.
  2. Local file identity is useful on the same filesystem when the platform provides it.
  3. Exact relative path plus compatible size/time is a strong suggestion, not portable proof.
  4. Filename and size are a low-confidence suggestion.
  • One candidate may satisfy one asset only.
  • Review all ambiguous candidates before link changes.
  • Apply accepted links in short transactions and retain unresolved items in the draft.
  • Root and per-file relink use the same operation and summary.

Duplicate and name conflict are different

Duplicate resolution

  • Skip incoming.
  • Keep both as two assets.
  • Use new location for the existing AssetId. Leave the prior file on disk.

Name conflict

  • Skip occupied destination.
  • Rename deterministically and preview it.
  • Replace after per-file acknowledgement and backup/restore placement.

Size, time, camera, and capture metadata narrow candidates. SHA-256 proves equality. Filename alone proves nothing.

Fingerprint coverage

  • Migration records missing fingerprints and a coverage count. It does not silently treat unindexed assets as unique.
  • A durable fingerprint-backfill operation hashes missing/stale present assets with bounded concurrency while the catalog is idle. It pauses, cancels, retries, and resumes across restart.
  • An import hashes its incoming file first. Before reporting Unique, it hashes every existing same-size asset whose fingerprint is missing or stale.
  • An unreadable, cancelled, or changing candidate produces not-fully-checked. The user may retry or continue with that limitation shown in the frozen plan and summary.
  • Backfill coverage is visible as indexed, remaining, failed, and unchecked counts.

Preset

  • Catalog-scoped, versioned, parsed, and migratable.
  • Constrained date, camera, original-name, and sequence tokens.
  • Preview resolved destination, filename, and collision result before Freeze.
  • Store title, caption, copyright, keywords, and a parsed Develop default.
  • Freeze the applied preset snapshot so later edits do not change an active job.

Auto Import

  • One enabled rule for the active catalog in release one.
  • Persist main-owned ingress, destination root, frozen preset reference, duplicate/conflict policy, and enabled state.
  • Reject unsafe ingress/destination overlap.
  • Require two unchanged no-follow size/time observations separated by the rule interval and a readable handle.
  • Deduplicate watcher events into one durable queue item.
  • Reuse manual import execution and preserve visible state across restart.

R6Catalog administration reference

Read this branch when: implementing step 13 or changing backup, validation, optimize, export/import, restore, retention, or corrupt-catalog behavior.
  • Portable catalog. Step 4 already exports a validated portable copy and opens/imports it as a new catalog for #129. Step 13 reuses that path and adds packages, merge, replace, retention, and restore.
  • Backup. Use SQLite online backup from the worker. Write schema/app versions, root mapping, timestamp, and SHA-256 for every package file. Publish outside the active catalog path.
  • Validate. Run checksum, integrity_check, foreign_key_check, location, and relation checks without mutation.
  • Optimize. Preview proven orphan and size counts. Build a compact temporary database, validate it, then swap under the writer lock.
  • Export/import. Export a validated package. Import opens as a new catalog by default. Merge and Replace require a conflict dry run and explicit choice.
  • Quiesce. Replace restore enters maintenance mode and reconciles every nonterminal file item while the current database still owns its operation journal.
  • Restore envelope. Before database replacement, atomically write target/safety checksums, restore stage, and a forward filesystem manifest outside the database. The manifest records current AssetIds, locations, fingerprints, current-only assets, and published mutation results.
  • Forward reconciliation. Restore the target into a temporary database. Apply current filesystem facts only. Existing assets keep their historical organization from the backup but receive verified current locations. Current-only files become recovered-after-backup. Unresolved facts remain in an explicit recovery queue.
  • Swap. Validate the reconciled temporary database, swap, reopen, and reconcile roots. Remove the envelope after every forward fact has a catalog row or recovery record.
  • Restore crash. Resume or roll back from the external envelope and safety backup. A journal inside the replaced database is never the only recovery source.
  • Corruption. Open read-only recovery mode when possible. Otherwise retain a registry entry that allows Validate, Restore, and raw evidence export.
