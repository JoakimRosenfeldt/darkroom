Darkroom / plan review

Ingest and catalog rework runbook

The architecture is right and the runtime it assumes actually works — I ran it. Three holes will bite during execution, and the verification burden it sets for itself has no harness to run on.

Reviewed against working tree at f92f2d4 13 steps, 13 issues 3 blockers, 6 significant, 4 minor

Verdict: proceed, after patching three gaps. Option A (per-catalog SQLite in a worker) is the correct call and I verified it runs in this exact Electron build. The identity model, the Electron-owned path authority, the five safe stages, and watcher-as-hint are all sound and all match real seams in the current code — the baseline evidence table is accurate, not decorative.

What is missing is not architecture. It is three places where a step depends on state no earlier step produces: duplicate detection needs fingerprints nothing backfills, catalog restore can silently orphan files already written to disk, and issue #129 — the catalog model itself — is absent from the issue map while steps 1–4 deliver its entire close gate.

Blockers

Blocker 1 Step 7 needs fingerprints that nothing produces

Step 7 requires comparing "incoming files with catalog assets" using SHA-256 as proof. But the migration reference says catalog-side hashing is lazy: "When root is online, scan and attach observations. Hash lazily." Nothing between step 2 and step 7 fills the fingerprints table.

So on a freshly migrated catalog, the first import either finds zero catalog-side duplicates — the feature silently does nothing, which is the failure mode users will not report — or it hashes the entire library inline, meaning a 40k-NEF library reads roughly a terabyte before the import dialog can render its review step.

Fix: add a resumable background fingerprint operation to step 2 or a step 7a, with its own progress and cancel, prioritized by the roots involved in the pending import. State the interim behavior in the UI: duplicate checking is partial until backfill completes, with a count of unhashed assets. Do not let step 7 close #21 while the answer depends on invisible backfill progress.

Blocker 2 Restore can orphan files already on disk

The operations and operation_items journals live inside the catalog database. Step 13 replaces that database wholesale during Restore, Replace, and Merge. The plan requires a validated safety backup first, which protects the catalog — it does nothing for the filesystem.

Concrete failure: a Move batch reaches destination-published for 300 of 500 files, the user restores yesterday's backup, and those 300 files now exist at their new location with no catalog row and no journal entry describing them. The plan's own invariant — "never leaves a partial pointer" — is broken by its own admin flow. A paused Auto Import queue has the same shape.

Fix: two rules in R6. First, refuse Replace and Restore while any resumable operation exists; require drain or explicit cancel, reusing step 4's writer-drain path. Second, after any restore, force a reconciliation pass over every root before the catalog goes live, so post-backup filesystem work is re-observed instead of lost. Add "restore with in-flight Move journal" to the R8 crash-recovery row.

Blocker 3 Issue #129 is missing from the issue map

#129 [Parity] Catalog model is open and its completion criteria are, almost verbatim, what steps 1–4 deliver: catalogs round-trip without lost ratings/labels/Develop/albums, source roots exist independently of last-folder settings, users can create/open/export/import/switch/repair, a missing root does not delete metadata. The plan assigns all of that to #26 and never names #129.

Two bad outcomes. The program hits its own finish line with #129 still open and nothing left to build for it, or someone later opens #129 as fresh work and proposes a second catalog contract on top of v3.

Fix: add #129 to the issue map with step 4 as owner and a Closes #129 in PR 4 (its export/import criterion may push the close to PR 13 — decide which, and say so). While there: #130 Smart Previews and #132 deleted-photo recovery both write to this schema. #132 wants a deletion ledger with retention state; audit_log is not that, and the asset health enum has no deleted state. Leaving room now costs one column; retrofitting costs a migration.

Significant gaps

4 No harness exists for the proof the plan demands

Step 9's gate is forced termination after each of five safe stages, for Rename, Move, Copy, and DNG. That is twenty kill-and-reopen runs, plus cross-volume, read-only destination, XMP mismatch, and changed-source cases. Step 6 wants per-architecture packaged probes. Step 12 wants restart mid-burst.

The repo has three node:test files (crop-geometry, nef-decoder-service, raw-utils) and scripts/capture-screenshots.mjs, which AGENTS.md already marks stale. R8 says "verify native behavior in the full Electron app," i.e. by hand, every PR. That is where this plan will actually stall.

Fix: fold a scenario harness into step 1, before the schema. Two pieces: fault-injection points named after the five safe stages so recovery is provoked in-process instead of by SIGKILL, and a headless Electron runner over the already-installed Playwright dependency. Then step 9's twenty cases are one table-driven test file rather than a day of manual work per PR.

5 One WAL connection serializes maintenance against reads

R1 specifies WAL with one worker connection, and gives that same worker backup, integrity_check, foreign_key_check, and compact. WAL's whole point is concurrent readers; a single connection gives that up. "Main stays responsive" is true and beside the point — the window paints, but every grid query queues behind a multi-minute integrity check on a large catalog.

Fix: open a second read-only connection for queries, or run maintenance in its own worker against the same file. Cheap now, invasive after step 4 hardens the worker protocol.

6 node:sqlite is experimental and unpinned

It works today — I confirmed it above — but it is still an experimental API in Node 24, and Electron majors move Node under you. The Decisions branch covers DNG licensing, Nikon redistribution, network Move, and backup retention, and says nothing about this. It is the single dependency the entire program rests on.

Fix: add a Decisions row. The worker request protocol from step 1 is already the adapter seam, so record that better-sqlite3 is the fallback and that the seam is what keeps the swap cheap. The repo already ships native modules via asarUnpack, so the fallback is viable, just not free.

7 Renderer read-model scale is undecided

Step 4 says "load persisted assets immediately," and today stores/library-store.ts (950 lines) holds every entry in memory. The plan never states a catalog size target, a windowing contract, or a query API — yet step 3 freezes the IPC shape that decides it. At 100k assets this ships every row across the bridge on open.

Fix: pick a target size now and give DarkroomLibrary a paged/filtered asset query beside the catalog methods. #173 owns the indexing work, but the contract that makes it possible is decided in step 3.

8 Five steps are too big for the plan's own one-PR rule

The plan says a larger PR hides failure boundaries, then puts schema plus migration (2), the full IPC rewrite (3), the transaction engine (9), the entire import UI with presets (10), and the whole admin suite (13) in one PR each. Realistically several thousand lines apiece.

Fix: relax the rule from one PR per step to one PR per provable invariant, and pre-split the five. Step 10 splits cleanly at preset CRUD / template preview / execution; step 13 at backup+validate / optimize / export-import-restore.

9 Cache re-keying has no migration or eviction story

Step 2 moves cache identity to catalogId:assetId:revision:variant. Today's entries are keyed by relativePath and lastModified in IndexedDB (lib/cache/aspect-ratio-cache.ts, develop-image-cache.ts). Every existing thumbnail becomes unreachable but not deleted, and the plan defines no purge for deleted assets or removed catalogs either. Cache grows forever.

Fix: one line in step 2's actions — drop the legacy IndexedDB stores on first v3 activation — plus a catalog-scoped cache eviction in step 4's close path.

Smaller notes

  • Legacy cleanup has no owner. R7 says keep legacy files "until user confirmation." No step defines who asks or when. Default: the JSON stays forever, which is safe but permanently confusing. Give it to step 4.
  • No undo for Rename/Move/Copy. #165 exists and is out of scope, but the operations journal is exactly the thing that would make undo possible. Worth one sentence saying whether the frozen plan is retained long enough to reverse.
  • Auto Import stops when the catalog is not active. Implied by "one enabled active-catalog rule" plus step 4's watcher teardown. True and defensible, but users will read "watched folder" as always-on. State it as a release-one limit in the UI copy, not just the schema.
  • Step 6's parallelism is thinner than it looks. It is marked parallel after step 3, but its format registry is what step 5's scan and step 7's candidate narrowing both read. Running it truly in parallel means steps 5 and 7 code against a registry that is still moving.

What the plan gets right

  • Option A is the correct choice, and the rejection of B is well argued — atomic JSON bundles do mean reimplementing transactions, indexes, and compaction in application code.
  • Identity before features. Stable IDs land in step 2, before anything mutates a file. The alternative ordering is how this kind of rework fails.
  • The five safe stages are the right decomposition, and pairing them with "publish by atomic rename, apply catalog after publish, clean source last" gives a genuinely recoverable Move.
  • "Watcher events are hints, reconciliation proves state" is the one rule that keeps filesystem watching from corrupting a catalog. It is stated early and repeated where it matters.
  • Capability registry over capability claims. Refusing to let a manifest edit promote camera support without sample output, and refusing to let the simulated Nikon helper carry a native label in production, are the two rules that make #134 and #135 closable at all.
  • The Refs/Closes protocol is precise — earlier PRs use Refs, the last proven PR closes, dependency issues get their own line. This is the part most plans hand-wave.
  • Baseline evidence is accurate. Every row I checked pointed at a real seam in the current code.

What I would change before step 1

  1. Add the fingerprint backfill operation and decide what duplicate detection reports while it is incomplete.
  2. Add the quiesce-and-reconcile rules to R6, and a restore-with-in-flight-journal row to R8.
  3. Add #129 to the issue map; leave schema room for #132's deletion ledger.
  4. Move the scenario harness into step 1 and make the safe stages fault-injectable.
  5. Add the second read connection, and a node:sqlite row in Decisions naming the fallback.
  6. Decide the catalog size target and put a paged asset query in the step 3 IPC contract.

Items 1–3 change what gets built. Items 4–6 change what it costs to build. None of them change the architecture.
