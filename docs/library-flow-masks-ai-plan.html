Run contract

Work one gated slice at a time.

Start at the earliest incomplete step in Ordered steps. Use the four leading words below as commands. A step stays open until every fact in its Gate is proven.

Read

Load the named context before editing.

Follow only the linked reference sections and issue contracts for the current step. Return here when the step changes.

Do

Implement the complete scoped slice.

Preserve unrelated work and use the smallest coherent change that satisfies the issue description and shared contracts.

Gate

Prove every listed completion fact.

Record the command, fixture, screenshot, package run, or recovery exercise that proves each fact. A partial pass leaves the step open.

PR

Create the pull request after the Gate passes.

Connect every relevant issue in the PR body and GitHub Development relationship. Use a closing keyword only for an issue whose full Gate passes.

Execution loop

  1. Find the earliest incomplete step and its first incomplete branch.
  2. Read the linked context and authoritative issue contract.
  3. Do the scoped implementation and preserve the locked seams.
  4. Gate the result with the named evidence. Record a failed fact and keep the step open when any check fails.
  5. PR the green slice using the connection and keyword rules in Pull request protocol.
  6. Continue only after prerequisite PRs are merged or the current branch is rebased on their accepted contracts.

Material assumption. Library flow covers Library selection and status, Develop edits, background execution and review, durable commit, reopen and Library status, then export. Pull request protocol

Every green Gate ends in a connected PR

  1. Create one reviewable PR for each green step or branch above.
  2. Connect every relevant issue in two places: the PR body and GitHub's Development or linked-issues relationship.

  4. Attach the exact Gate evidence. Link artifacts and record commands plus observed results.
  5. List deferred Gates and their next PR. Keep every partially implemented issue open.

User flow

One flow from Library to export

1. LibraryOpen an asset by stable ID and source revision. Show derived-job status on the thumbnail and in a global jobs drawer.
2. DevelopEdit a v3 recipe through ordinary undoable commands. The masking panel has a tree and a selected-node inspector.
3. RunStart local selection or enhancement jobs. Start remote removal only after the visible consent step.
4. ReviewJob output stays staged. The user sees progress, cancellation, retry, before/after, alternatives, and stale reasons before acceptance.
5. ExportUse the same compiled evaluator. Export blocks missing or stale required artifacts, with recompute, disable, or cancel actions.

Library and jobs

  • A thumbnail badge shows running, review-ready, failed, stale, or missing-derived-data state without replacing pick/rating badges.
  • A compact global drawer keeps jobs visible across entry changes and Develop exit. It shows stage and honest indeterminate progress when total work is unknown.
  • Opening a review-ready entry restores its staged before/after state. Closing the panel does not cancel work.
  • Cancel is idempotent. Retry creates a new operation ID and retains the last accepted output.

Masking workspace

  • The tool picker inserts Brush, Linear/Radial Gradient, Luminance Range, Color Range, Depth Range, Subject, or Sky.
  • The mask tree exposes group precedence, add/subtract/intersect, invert, enable, reorder, duplicate, and delete. Focus stays on the nearest surviving node after a structural edit.
  • The selected-node inspector owns source controls. A separate selected-mask inspector owns Basic and local effect groups.
  • The canvas footer keeps overlay color/opacity and brush display controls only.

Enhance panel

  • Separate Denoise, Raw Details, and Super Resolution actions show model availability before start.
  • One active accepted source variant is supported in v1. Starting another job previews replacement of that variant, not an implicit processing chain.
  • Before/after, progress, cancel, retry, Accept, and Reset are explicit. Accept is one history entry.
  • Accepting a changed source variant lists dependent masks and cleanup patches that will become stale.

Generative Remove panel

  • Paint a removal region, review its bounded crop and margin, provider, upload dimensions, metadata policy, and consent text before Submit.
  • Progress never claims a precise percentage the provider does not supply. Cancel is best effort and never means a remote request definitely stopped.
  • Review alternatives locally. Accept one patch, retry with a new consented request, or reject all. Only accepted patch ref and permitted provenance enter the document.
  • An accepted patch remains available for offline preview/export. No missing patch is re-requested automatically.

Invalidation is typed. A source-content or active-enhancement change stales source-derived raster artifacts and cleanup patches. Manual and analytic range nodes use source-normalized definitions and reevaluate on the new mask-analysis-v1 basis. Subject/Sky FrameRevision includes crop and orientation, so either change marks the accepted matte stale with a reason. The policy is serialized so later versions do not reinterpret old results.

Global settings, source processing, accepted cleanup refs, mask expressions, local adjustments, source/frame policy, and provenance. It changes only for an edit or atomic acceptance.

Artifact repository

Immutable derived data

Alpha mattes, depth maps, RGB source variants, frozen removal selections, and RGBA cleanup patches. New bytes are external and content-addressed.

Intent, operation ID, revisions, progress stage, cancellation token, private staging, provider state, retries, and recovery journal. Job progress is not document history.

There is no mask-level inverted field in v3. One canonical tree has one meaning. Every numeric range, sample-count bound, algorithm version, analysis policy, and artifact reference is validated from unknown before it reaches a renderer or store.

Versioned evaluation order

immutable original decode
  → one accepted enhancement source variant, if any
  → accepted cleanup patches for that exact source/frame revision
  → orientation into source-normalized mask-analysis-v1
  → analytic and raster mask coverage on mask-analysis-v1
  → crop/geometry mapping into the render target
  → global Basic, curve, mixer, and tone/color stages
  → coverage-weighted local parameter-field accumulation
  → versioned local kernels
  → global effects, output transform, and target sink

mask-analysis-v1 is before crop and all global/local Develop adjustments. Luminance and color ranges therefore do not move when Exposure or Saturation changes. Manual and analytic sources use normalized source coordinates. Subject/Sky keep their model-specific input transform and a FrameRevision that includes crop and orientation; Depth keeps its own map-to-source transform. Accepted enhancement and cleanup changes create a new analysis revision.

Composition and local effect rules

Alpha v1 recommendation

  • Add: 1 - (1-a)(1-b), matching current source-over union.
  • Subtract: a(1-b), matching current destination attenuation.
  • Intersect: ab.
  • Invert: 1-a.
  • Clamp once at evaluator boundaries. Preserve current v2 8-bit rounding in compatibility mode.

Local v1 recommendation

  • Accumulate coverage-weighted fields across all enabled masks, then clamp once so mask order does not change the result.
  • Version the order: Basic, Colorize, Texture, Clarity, Noise, Moire, Defringe, Sharpness.
  • Neighborhood kernels read the pre-local working buffer and blend the result by accumulated coverage. Do not copy a global kernel until that blend is proven.
  • Every control has typed zero/default, bounds, reset, one history gesture, and an explicit unsupported state.

Logical and device limits

The parser keeps bounded document bytes, total nodes, depth, samples, strokes, and points for hostile input. The renderer separately records a capability snapshot from texture size/formats, scratch memory, model memory, and measured allocation failures. Phase 0 should try a target of at least 64 logical masks and 256 nodes per mask with bounded 2,048-pixel analysis tiles, then set supported limits from actual minimum hardware. Existing larger documents open read-only with diagnostics; a new edit that exceeds the active budget is rejected before history or persistence. There is no silent lower-quality algorithm and no new full CPU renderer.

Job state and atomic acceptance

queued → preparing → running → postprocess → awaiting-review → accepting → accepted
            ↘ cancelled   ↘ failed      ↘ interrupted      ↘ stale
  1. Start journals immutable intent, operation ID, source/frame/document revisions, model/provider revision, parameter hash, and private staging location.
  2. Execution checks an abort token between stages or tiles. A remote cancel is best effort. No job mutates the document while running.
  3. Accept rechecks job token, stable source/frame revision, expected Develop revision, provider consent, and active device support.
  4. The artifact repository verifies hash, encoding, dimensions, and byte limits, then atomically publishes the content-addressed bytes.
  5. A recovery record binds that artifact to one complete Develop operation. The repository validates and commits it with the expected revision. This is one workspace call, not two UI calls.
  6. The job becomes accepted only after the document commit is durable. XMP projection is queued separately. A crash replays the idempotent record; an unreferenced published artifact stays protected until reconciliation.

Failures use a bounded taxonomy: cancelled, interrupted, stale, model-unavailable, unsupported-input, device-limit, privacy-limit, provider-error, integrity-error, and filesystem-error. Each maps to one recovery action. The previous accepted output remains active during retry.

Compatibility and persistence

Do not trade old edits for a cleaner schema

Coordinate with catalog v3. The companion library migration should copy the current Develop payload into its first immutable revision without rewriting mask internals. This plan then performs the v2-to-v3 mask migration on load and on the first accepted v3 edit. That avoids a second catalog migration and keeps the original v2 bytes as recovery evidence.

V2 to v3 sequence

  1. Read without mutation. Parse the catalog/XMP envelope from unknown. Keep strict v2 validation. A newer envelope or unknown v3 node opens as raw read-only recovery state and is never overwritten by an older writer.
  2. Resolve identity. Map the old entry ID through the companion migration aliases to SourceId. Attach the current content revision when proven. Otherwise retain a legacy-stat source revision and mark it less authoritative.
  3. Translate in memory. Copy global settings and mask IDs/order/enabled state. Left-fold each old ordered component with its exact current add/subtract math. Wrap the root in one invert node if the old mask was inverted. Do not keep both representations.
  4. Default without visual change. Copy old BasicSettings. Set Texture, Clarity, Sharpness, Noise, Moire, Defringe, and Colorize amount to zero. Keep brush points and controls unchanged.
  5. Preserve old AI output. Keep model ID/revision, source signature, 512×512 or 384×384 input, threshold, matte dimensions, hash, and PNG bytes. Do not rerun, resample, refine, or reinterpret the matte during migration.
  6. Externalize transactionally. Stage each legacy inline PNG, verify its recorded hash/dimensions/size, publish by content hash, validate the v3 ref, then commit the v3 document with expected revision. If any step fails, keep the v2 document and inline bytes authoritative.
  7. Prove before enabling writes. Compare overlay, Develop, reopen, XMP/catalog round-trip, and export against pinned v2 fixtures. Enable the v3 writer only after the compatibility evaluator meets the agreed pixel tolerance.

Durable commit and sidecar projection

  1. Validate the complete proposed v3 document, logical limits, referenced artifact metadata, and expected parent revision.
  2. Publish new immutable artifact bytes and keep an acceptance journal that names the intended document operation.
  3. Commit the new Develop revision through the companion repository. The catalog manifest/revision becomes authoritative.
  4. Project compact v3 mask intent, refs, and permitted provenance to XMP by atomic replacement. Full RGB, depth, provider payloads, credentials, and model files never enter XMP.
  5. If XMP fails, leave the catalog edit committed and expose pending/error state. Retry from the projection journal. Do not use timestamps to guess away a conflict.
  6. On startup, reconcile published artifacts, document commits, job acceptance receipts, and sidecar projections idempotently before garbage collection.

Portability and backup

  • All new binary artifacts are external. The first release does not selectively embed "small enough" new mattes because that creates two ownership paths and can recreate the 16 MiB limit.
  • A catalog backup includes its Develop revisions, acceptance/projection journals, artifact manifest, every referenced artifact, hashes, and model/provider provenance. Model downloads may be reacquired and do not need backup.
  • A sidecar moved alone opens intent and provenance with a clear missing-artifact state. It never silently recomputes a different result.
  • A later portable bundle may package sidecar plus artifacts after measured demand. It is not required to implement the ten issues.

Retention and collection

  • Retain artifacts referenced by the current document, persistent revisions/snapshots, undo/redo checkpoints, an awaiting-review job, acceptance/projection journal, or an in-progress backup.
  • Reset and reject remove document/job refs but do not synchronously delete bytes. A grace-period collector removes only verified unreferenced artifacts.
  • Legacy Base64 is eligible for retirement only after v3 commit, successful reopen, artifact verification, and rollback-window expiry. It is never duplicated indefinitely inside v3.
  • Relink compares artifact hash and metadata, never filename alone. Corrupt data is quarantined and remains diagnosable.

Out of scope

Batch AI edits, object/background/people/landscape selection, cloud accounts or sync, generative upscale or sharpening beyond #73, source-file modification, a catalog database choice, and a renderer rewrite are out of this plan.
