# Rust desktop migration

Darkroom now uses Tauri 2 as its desktop host and Rust for local state, file access, background work, and export encoding. React, Vite, the Develop shader pipeline, and the LibRaw WASM decoder remain in the renderer. The packaged app does not run Electron or a Node sidecar.

The typed renderer bridge still exposes the existing `darkroom:*` operations. An audit matched all 122 original IPC channels to [`src-tauri/src/commands.rs`](../src-tauri/src/commands.rs), including argument counts. [`src-tauri/src/lib.rs`](../src-tauri/src/lib.rs) authenticates the main webview, dispatches commands, and owns shared catalog and Develop services. Asset reads and export pixels use binary IPC; ordinary requests and results use JSON. Catalog and session IDs, revision checks, cancellation, and progress events remain part of the command contract. The channel audit is a coverage boundary, not a claim that each command has its own GUI test.

The Rust host reuses the Electron app-data location and existing SQLite catalogs, settings, presets, camera profiles, Develop assets, sidecars, and recovery journals. Legacy v1/v2 catalogs migrate through a staged, validated database; v3 catalogs are upgraded on activation. Import and batch work retain their journals so interrupted operations can resume or recover. Rust resolves photo paths from the active catalog and validates them before opening files; the renderer cannot supply arbitrary file paths for approved assets.

[Legacy migration probe results](rust-migration-checks.json) record successful v1/v2 imports, database integrity, preserved originals, and matching recovery snapshots.

The existing 244 checks passed on Node 24, and the real desktop JPEG and NEF smoke runs passed on Linux. CI builds the release GUI and diagnostic backend on Linux, macOS, and Windows, and runs the JPEG desktop workflow on Linux. Build success does not establish GUI or package qualification on every platform. The Electron source and its tests remain as reference material; they are not shipped or used as a runtime fallback. The current build and desktop commands are in the [README](../README.md), and the platform build matrix is in [native CI](../.github/workflows/native.yml).

Builds require Rust, a C/C++ compiler, libclang, and the target platform's Tauri webview prerequisites. SQLite, WebP, and LibRaw are built from bundled source. macOS release packaging requires the private Nikon SDK: the release script stages and signs its helper and frameworks, checks the helper checksum, and preserves the SDK's `prm.bin` resource layout. Packaging fails if that runtime is unavailable. Windows and macOS packaging require validation on their own runners; a Linux desktop pass cannot establish those results.

Native camera-profile verification uses LibRaw 0.22.1, matching the LibRaw version in `libraw-wasm` 1.6.0. The earlier native 0.21.1 bundle decoded a lossless Nikon Z6 III sample but returned an identity colour matrix, which the verifier correctly rejected. Version 0.22.1 supplies the camera matrix; independent native probes passed for both Z6 III and D500. This restores profile verification without weakening its checks. A [public Z6 III lossless sample](https://www.photographyblog.com/reviews/nikon_z6_iii_review) passed all nine desktop workflow checks on Linux WebKit, including GPU preview/export, 100% detail, recovery, and unchanged source hashes. High Efficiency NEF decoding remains a separate decoder capability.

The vendored IPTC reader retains TIFF parsing but omits its unconditional format notices. Real backend checks found unchanged extracted metadata for JPEG, PNG, and NEF and clean diagnostic JSON output. Failed thumbnails now show their error reason instead of only “Error”; a truncated NEF and a healthy JPEG verified the failure and success states in WebKit. A reported macOS Z6 III loading failure still needs an affected file or its detailed error to confirm its cause.

The [performance report](performance/README.md) includes same-machine Electron-versus-Tauri desktop measurements at matching viewport sizes, isolated CPU kernels, raw samples, and workflow screenshots. Catalog import, idle memory, and native kernels improved in those runs; startup through automation and loaded-library memory did not. The report separates measured gains, regressions, and limits rather than claiming an application-wide speedup.
