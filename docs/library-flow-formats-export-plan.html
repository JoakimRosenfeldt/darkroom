Mission and completion bound

Build two programs in sequence. Program A is the local media and export engine. Program B is connected delivery. The local engine must work without an account or network. Connected delivery must reuse its immutable recipes, jobs, files, and destination boundary.

Program A, stages 0 to 5

Local media and export

DNG, camera RAW, HEIF, TIFF, high-bit output, original copy, quality, naming, resolution, PPI, ICC, metadata, alpha, watermark, presets, large files, and Content Credentials.

Program B, stages 6 to 8

Connected delivery

Durable publish state, multiple destinations, provider adapters, print partners, contributor and editor roles, QR links, and embeds.

Whole-program completion criterion

On every claimed packaged desktop target, each recognized fixture completes import, Develop, reopen, and the selected export with the declared format, dimensions, orientation, provenance, profile, precision, alpha, metadata, and delivery result. Unsupported input fails before mutation with a per-file reason. Source hashes stay unchanged. Restart, cancellation, collision, retry, and partial failure never present an incomplete file as complete. Existing JPEG, PNG, WebP, and NEF behavior still passes.

Connected delivery is complete when publish state survives restart, secrets remain outside catalogs and jobs, the service rejects every unauthorized action, and provider failures leave an item-level recovery action plus a local package where possible.

Hard boundary

The current renderer returns one full 8-bit RGBA buffer over IPC. The encoder strips alpha. New controls must not claim 16-bit output, alpha preservation, bounded large output, or color-managed fidelity until the replacement path proves those facts. This is the main design constraint.

Execution loop

Run these steps for every pull request unit in the stage plan. A unit is complete only after step 6.

1

Load the branch context

Read the root AGENTS.md, the live GitHub issues named by the unit, and the matching cards in Issue reference. If the unit changes Next.js code, read the relevant guide in node_modules/next/dist/docs/. Inspect the current worktree before assuming this baseline still applies.

Pointer: issue cards define the requested outcome. Repository source defines current behavior.

Complete when the unit notes its issue links, dependencies, files in scope, contracts that must stay stable, and verification evidence.

2

Check the dependency gate

Confirm every earlier contract used by the unit is merged or present on the branch. Re-run the relevant capability probe when a native library, packaged target, provider API, or hosted service may have changed.

Pointer: use Work graph for order and Fixed decisions for choices the unit may not reopen casually.

Complete when each dependency has a commit, artifact, or written verdict. An inconclusive native or service gate blocks the dependent claim.

3

Resolve the contract first

Update the smallest shared type, registry entry, migration, or adapter contract needed by the unit. Keep filesystem access, credentials, native calls, and service data at their owning boundary. Keep recipe and preflight logic pure.

Pointer: load only the relevant rows in Domain contracts and Architecture reference.

Complete when impossible states have no representable success path and every new persisted value has a version or migration.

4

Implement one coherent slice

Follow existing repository patterns and keep the diff inside the unit scope. Include truthful unavailable and failure states. Preserve unrelated user changes. Keep old readers until the new writer and migration have passed.

Complete when the user-facing path, boundary implementation, recovery path, and cleanup path all use the same resolved contract.

5

Prove the claim

Run existing checks, the focused artifact check, npm run build, and the real Electron path when the unit touches IPC, native code, persistence, rendering, or export. Inspect output files with an independent tool. Record existing warnings separately from new failures.

Pointer: Verification is the evidence contract. New automated tests need explicit user authorization under repository rules.

Complete when every acceptance statement for the unit points to a passing artifact on each claimed target. A UI label is not evidence.

6

Open the connected pull request

Use the repository file-pr workflow. Open a focused pull request. Connect every affected issue in the body. Use Refs #N for partial work and Closes #N only when this pull request satisfies the whole issue card.

Pointer: follow the exact body and closure rules in Pull request protocol.

Complete when a pull request URL exists, GitHub shows the issue connections, the body contains verification evidence, and one final pull request owns closure for each completed issue.

Pull request protocol

A commit is not the handoff. Every implementation unit ends with an open pull request. The pull request must connect its issues through GitHub keywords.

Connection rules

  • Use Refs #89 when the pull request supplies a dependency, experiment, shared contract, or partial implementation.
  • Use Closes #89 only when all completion checks in the #89 card pass on every claimed target.
  • List every affected issue. A shared registry change may reference several issues even when it closes none.
  • Assign one closure owner to each issue. Earlier pull requests use Refs. The final qualifying pull request uses Closes.
  • Keep unrelated issues out of the closing list. Mention a dependency without claiming delivery.

Domain contracts

These are behavioral contracts, not final filenames or exact TypeScript shapes. Match repository patterns when implementing them.

Media format

Stable format ID, suffixes and optional sniff rule, decoder adapter, runtime status, input facts, output descriptor, provenance modes, and support note.

Complete when every consumer asks the registry instead of maintaining its own format list.

Decode result

A decoded result carries dimensions, channels, precision, alpha, profile, orientation, normalized metadata, provenance, warnings, and source revision. Unavailable and failed results carry stable reason codes and user actions.

Complete when missing capability cannot masquerade as a generic image.

Export recipe

Original is a byte-copy policy. Rendered contains format, output descriptor values, dimensions, PPI, profile, precision, metadata policy, alpha policy, watermark, naming, and destination choices.

Complete when Original and Rendered cannot form one ambiguous object.

Resolved plan

Immutable source revision, Develop revision, resolved output name, encoder facts, dimension result, memory and disk estimate, warnings, destination capabilities, and recipe schema version.

Complete when retry never re-reads changed UI or preset state.

Job and item state

Queued, planning, rendering, encoding, signing, delivering, completed, failed, cancelled, and needs-review states with stage-owned temp artifacts and per-item results.

Complete when restart can reconcile every nonterminal state without guessing.

Destination

Capability probe, preflight, submit, status, retry, cancel, disconnect, result link, credential reference, and local fallback.

Complete when a provider cannot bypass local rendering, privacy, naming, or job state.

Publish fingerprint

Issue #108 needs a stable answer to "Modified since what?" Hash the source identity, source revision, Develop document, resolved rendered recipe, metadata policy, and destination capability version. Filename and modification time are not enough.

Migration and recovery rules

Settings

  1. Add a schema version and reject unknown future versions without overwriting them.
  2. Map current format, quality, lossless, size, suffix, and conflict values into a Rendered recipe.
  3. Use metadata None, sRGB, 8-bit, no watermark, and no credentials for migrated values. Preserve the current opaque-file result.
  4. Store the migrated recipe as last-used. Let the user name presets.
  5. Write a validated temporary file, rename atomically, and retain one good backup until the next successful launch.

Catalog v3

  1. Delay the broad catalog migration until Stage 6. Stages 0 to 5 do not need publish history.
  2. Generate stable asset IDs and copy metadata, albums, archive state, and Develop documents into a temporary v3 snapshot.
  3. Retain missing asset records. Mark them missing so Deleted, relinked, and previously published states remain representable.
  4. Add destinations, preset IDs, and publish fingerprints. Keep active job journals outside the catalog snapshot.
  5. Validate every reference before rename. Keep v2 unchanged until v3 opens successfully.

Cancellation and recovery

  • Planning cancellation mutates no destination.
  • Rendering stops at the next validated tile boundary. The stage that owns a temp artifact removes it.
  • Encoding and C2PA write private temp files. Only inspected output receives the final destination name.
  • Retry uses the original immutable plan and resolved name.
  • Completed items stay completed when a batch cancels. The summary reports partial completion.
  • Provider submission uses an idempotency key when supported. Unknown remote state becomes Needs review.

  4. Run the real Electron path when the unit touches rendering, IPC, files, persistence, native code, or UI.

Issue closure rule

Code presence does not close an issue. The closing pull request must map every requirement in the matching issue card to a passing artifact on each claimed target. It must preserve the existing regression matrix and state unsupported cases honestly.

#89 DNG import, edit, and export

Stage 3A

Requested outcome
